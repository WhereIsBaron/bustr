## Releasing / auto-update (set up 2026-08-17, v2.20.1)
The script declares `@updateURL`/`@downloadURL` pointing at the **`release` branch** raw URL
(`https://raw.githubusercontent.com/WhereIsBaron/bustr/release/bustr.user.js`). Userscript
managers poll that branch, so users on a GitHub install auto-update from it.
- **`main` is NOT the update source.** It auto-commits work-in-progress ("session progress"
  commits) and auto-pushes, so it must never be what users pull, or half-finished edits would
  ship. `release` only moves when you deliberately advance it.
- **To publish a vetted build to auto-update users:** fast-forward `release` to the reviewed
  commit on `main` and push it:
  ```
  git push origin main:release
  ```
  (Ships `main`'s current tip. To ship a specific older commit instead: `git push origin <sha>:release`.)
- Bump `@version` + `SCRIPT_VERSION` + add a CHANGELOG entry BEFORE advancing `release`, or the
  managers won't see a newer version and won't update.
- **GreasyFork is a separate channel** (`greasyfork.org/en/scripts/585973`, on 2.17.1): those
  users update through GreasyFork, not this branch. A GreasyFork upload is still a manual step.

### Cloud sync (new in v2.13.0)
- Optional, **opt-in, default OFF** cross-device sync of bust history. Backend is Firebase (Firestore + custom-token auth) fronted by a Netlify function; client wiring is the `CloudSync` engine in `bustr.user.js`. Full spec in `cloud/CLIENT_INTEGRATION.md`; backend setup in `cloud/SETUP.md`.
- **The synced doc stores a model-relevant snapshot** (`profileSnapshot()` in `CloudSync`), for cross-user model work. Stored fields on `busts/torn_<id>`: `log` (each entry `h,pred,pen,success,jailed,lvl,cal,ts,m` - `lvl`/`cal` added v2.15.1), `perks`, `level`, `sv` (script version), `cal` (effective calibration), `selfCalVal`, `pda`, `settings` (perkCal/selfCal/calOverride/playStyle), `updatedAt`. These mirror the model-useful fields of the debug export; the diagnostic/DOM/apiKey/timestampsArray parts are deliberately NOT synced. API key/name/ID/faction never stored. **If what's synced changes again, update ALL disclosures together**: consent modal, `cloudsync` help, `#bustr-set-cloudsync` hint (all in `bustr.user.js`), plus `GREASYFORK_LISTING.md` and `FORUM_POST.md` (ToS table + cloud paragraph) and `cloud/SETUP.md`.
- **Not desktop-only (corrected in v2.15.2).** The feature is gated purely on `hasGMXhr` (is `GM_xmlhttpRequest` present), NOT on desktop-vs-PDA. Recent Torn PDA provides `GM_xmlhttpRequest` natively and honours `@connect` (confirmed via Torn PDA docs/forum, 2026-08-07), so sync works on desktop AND PDA - enable on both and they merge to one history keyed to the Torn ID. Where the capability is absent (older PDA builds / minimal managers) the section shows "unavailable" and no-ops. The old "desktop only" copy was wrong and was removed everywhere. Requests go via `GM_xmlhttpRequest` to bypass torn.com's connect-src CSP (plain fetch is blocked on-page on both platforms).
- The API key is **never uploaded** - it goes only to Torn's own API and, once, to the verification function (which uses it to confirm player identity, then discards it; never stored server-side). The only server secret is the Firebase service-account JSON, held solely in Netlify env var `FIREBASE_SERVICE_ACCOUNT`.
- Backend passed its private 5-step test (verify -> sign in -> write -> read -> cross-user isolation denied). Client code is written and passes `node --check`, ASCII-clean, no auth leak into the debug export. **Live on-torn.com behaviour is NOT yet tested** - see next steps.

The box stays open when the injected key is missing/empty, the wrong length, or being rejected.

- **Browser password-autofill (FIXED v2.15.0):** the panel key field was `type="password"`, which triggered the browser's built-in password manager to offer autofill in nearby Torn text boxes (e.g. chat search); it stopped when BUSTR was disabled. ## Model recalibration - FIRST FIX SHIPPED v2.16.0 (2026-08-07)
**Penalty saturation shipped.** `PENALTY_SATURATION_PCT = 95`: `effectivePenalty = PENALTY_WEIGHT * min(penaltyPct, 95)` in `calcSuccessChanceRaw` (nothing else changed, so low/mid penalty untouched). Fixes the "everything floors to 16% at high penalty" defect. Validated per the standing rule on 134 reconstructable records (10 users): the OLD model scored Brier 0.30 (WORSE than the 0.24 base-rate guess; 60/134 records pinned to a rail); the cap passed leave-one-out at ~0.234, stable with AND without the heaviest user (excl-heavy 0.301->0.224), cap value stable ~pen 91-97% across folds, and every candidate form beat current - so it is not overfit. Also restores self-cal at high penalty (it maxed uselessly before because the flooring came from the penalty term it cannot touch). Did NOT bump OUTCOME_MODEL_VERSION (stored pen unchanged). The fit was done via `cloud/dump_enriched.js` + scratch analysis (`analyze.py`/`robust.py`).

Still open on the model:
- **Refine the 95% cap** as more `lvl`/`cal`-stamped data accumulates (it is a first fit on 134 records). Re-run `cloud/dump_enriched.js` and re-fit. Records now carry `sv`, so distinguish pred from capped (sv>=2.16.0) vs uncapped formulas when recomputing.
- **Top rail: SHIPPED v2.20.0.** The predicted top bucket really was over-confident, now confirmed at scale: on 1224 reconstructable records (26 users) the current model showed ~81% where actual was ~65%, and scored Brier 0.2455 - fractionally WORSE than the 0.2436 base-rate guess (correct ordering, no calibrated skill left). Fix was a shrink refit, not the logistic switch: `PRED_SHRINK_K` 0.65 -> 0.40 (centre unchanged at 45), grid-searched to minimise pooled Brier. Passed leave-one-out (in-sample 0.2350 == LOO 0.2350; now beats base rate). Displayed range tightens ~16-81% -> ~27-67%. A logistic SHAPE switch is still the cleaner long-term move to remove both rails smoothly; only pursue if residual miscalibration persists with more data. Smaller residual left alone: hardness 300-700 (low-penalty) runs ~10-20pts over-confident - revisit once high-hardness volume grows.
- **Perk-aware-by-default: SHIPPED v2.17.0.** Validated on synced data (`cloud/dump_perkval.js` + scratch `perkval.py`): perk-derived calibration beats the fully-perked baseline for under-perked users, meaningfully at low/mid penalty. Turned ON by default (success/skill term only) + one-time migration for existing users (`perkCalDefaultApplied` flag) + parse-confidence guard. **Key decoupling:** `usePerkCalibration` used to also drive the penalty calc (`getPenaltySkillCalibration` -> `penaltyPctAt`); that was validated only with baseline penalties, so v2.17.0 made `getPenaltySkillCalibration` return baseline (never perk-derived) - penalty stays on the originally-validated model, avoiding the v2.7.19-style calibration-in-denominator coupling. Per-user adaptation now: level + perks (default) + self-cal (overrides at >=100 samples) for success; baseline (or manual override) for penalty. See [[bustr-model-followups]].

### Original finding that led to the fix (2026-08-07, from the first cross-user data analysis)
Ran `cloud/aggregate.js` against live Firestore: **13 users, 899 records (765 current-model m:2)**. First real cross-user look at the success model. `aggregate.js` was improved this session to (a) filter to `m:2` only (134 legacy rows have inflated pen / pred artifacts and were polluting the buckets) and (b) add a calibration-by-predicted-bucket table. Re-run it anytime with `cd cloud && node aggregate.js` (needs `npm install` once; it reads the gitignored `*adminsdk*.json`).

Findings (m:2 only):
- **Overall calibration is excellent on the mean:** 59.8% predicted vs 62.5% actual. But that hides an offsetting shape error at the two ends.
- **Penalty response is too steep.** Low penalty (0-79%) is over-predicted (~77-81% shown vs ~52-77% actual); high penalty (130-199%) is drastically UNDER-predicted - the model floors those to ~16% but they actually succeed ~68-90%. In the calibration table, the whole `pred ~16%` bucket (n=116) succeeds **67%**. Top buckets (pred 70-89, n~377) are ~10pts over-confident.
- Diagnosis: the linear `-2.0*penaltyPct` term (calcSuccessChanceRaw) over-penalises at the high end; penalty's real marginal effect saturates. This is exactly the "saturating curve" the v2.8.0/v2.10.0 notes predicted we'd need "once we have more than one player's data." We now do.

**Why no model change shipped yet (do NOT skip this):** a rigorous leave-one-out (the standing rule; the raised-floor idea already passed in-sample and FAILED LOO once) needs to recompute each record's prediction from its inputs - but historical records store only `h, pred, pen, success, jailed, ts, m`, omitting the `level` and `calibration` the formula needs, and stored `pred` mixes pre/post-shrink displays. So the data on hand cannot validate a fix.

**What was done instead (v2.15.1):** every new outcome now also logs `lvl` + `cal` (the exact inputs used), so future records are fully reconstructable. These sync for opted-in users, so cross-user enriched data will accumulate.

**Pipeline VERIFIED (2026-08-07):** `cloud/validate_enriched.js` recomputes each enriched record's prediction from its `h/pen/lvl/cal` and compares to the stored `pred` - 131/132 exact (99.2%), 1 off-by-one rounding, 0 real mismatches. So the captured data is internally consistent and trustworthy; the recalibration just needs volume. Latest aggregate: 16 users, 1311 m:2 records, but only ~132 enriched (lvl+cal) so far - the old ~1180 predate 2.15.1 and can't be backfilled. Data is well-spread (top user 28%). Signal unchanged and strong: ~40% of records floored to pred~16% but succeed ~55%; overall 46.5% predicted vs 59% actual. Re-run `cd cloud && node aggregate.js` (and `validate_enriched.js`) to track enriched-count growth; fit when it reaches a few hundred with good high-penalty coverage.

**This plan was EXECUTED 2026-08-17 (shipped the top-rail shrink refit, v2.20.0 - see above).** Kept here as the reusable recipe for the next refit:
1. Dump enriched m:2 records ({h, pen, success, lvl, cal}) - `aggregate.js` reports counts; a sibling script does the per-record recompute.
2. Recompute current-model prediction per record from h/pen/lvl/cal, replicating `calcSuccessChanceRaw` EXACTLY as it currently ships (v2.20.0): skill=lvl*cal; raw=266.6-(0.28*60/skill)*h-2.0*min(pen,95); shrink 45+0.40*(clamp(raw,1,100)-45). Keep the `min(pen,95)` saturation cap (v2.16.0) and the 0.40 shrink (v2.20.0) in sync with the script or the recompute is wrong.
3. Fit + **leave-one-out** candidate forms (further penalty-curve tweaks, and/or the linear->logistic shape switch that would remove both rails) vs the current model on Brier. Ship ONLY what beats current out-of-sample. Constants stay principled, not per-player-overfit. See [[bustr-model-followups]].
