### Cloud sync (new in v2.13.0)
- Optional, **opt-in, default OFF** cross-device sync of bust history. Backend is Firebase (Firestore + custom-token auth) fronted by a Netlify function; client wiring is the `CloudSync` engine in `bustr.user.js`. Full spec in `cloud/CLIENT_INTEGRATION.md`; backend setup in `cloud/SETUP.md`.
- **The synced doc stores a model-relevant snapshot** (`profileSnapshot()` in `CloudSync`), for cross-user model work. Stored fields on `busts/torn_<id>`: `log` (each entry `h,pred,pen,success,jailed,lvl,cal,ts,m` - `lvl`/`cal` added v2.15.1), `perks`, `level`, `sv` (script version), `cal` (effective calibration), `selfCalVal`, `pda`, `settings` (perkCal/selfCal/calOverride/playStyle), `updatedAt`. These mirror the model-useful fields of the debug export; the diagnostic/DOM/apiKey/timestampsArray parts are deliberately NOT synced. API key/name/ID/faction never stored. **If what's synced changes again, update ALL disclosures together**: consent modal, `cloudsync` help, `#bustr-set-cloudsync` hint (all in `bustr.user.js`), plus `GREASYFORK_LISTING.md` and `FORUM_POST.md` (ToS table + cloud paragraph) and `cloud/SETUP.md`.
- **Not desktop-only (corrected in v2.15.2).** The feature is gated purely on `hasGMXhr` (is `GM_xmlhttpRequest` present), NOT on desktop-vs-PDA. Recent Torn PDA provides `GM_xmlhttpRequest` natively and honours `@connect` (confirmed via Torn PDA docs/forum, 2026-08-07), so sync works on desktop AND PDA - enable on both and they merge to one history keyed to the Torn ID. Where the capability is absent (older PDA builds / minimal managers) the section shows "unavailable" and no-ops. The old "desktop only" copy was wrong and was removed everywhere. Requests go via `GM_xmlhttpRequest` to bypass torn.com's connect-src CSP (plain fetch is blocked on-page on both platforms).
- The API key is **never uploaded** - it goes only to Torn's own API and, once, to the verification function (which uses it to confirm player identity, then discards it; never stored server-side). The only server secret is the Firebase service-account JSON, held solely in Netlify env var `FIREBASE_SERVICE_ACCOUNT`.
- Backend passed its private 5-step test (verify -> sign in -> write -> read -> cross-user isolation denied). Client code is written and passes `node --check`, ASCII-clean, no auth leak into the debug export. **Live on-torn.com behaviour is NOT yet tested** - see next steps.

## Fresh user feedback (2026-08-03, from the Torn forum thread)
- First real public feedback, positive ("just tried it, its kinda awesome!") - matches the second cloud user (`torn_3270760`) now syncing. People are installing it.
- **PDA double key-entry confusion (implemented in v2.15.0, awaiting PDA verification):** a PDA user noticed they can enter the API key TWICE - once during script install (the PDA app's own `###PDA-APIKEY###` injection) and again in BUSTR's settings panel key box on the jail page. It reads as redundant. Background: the panel key box is intentional (added v2.8.8) - it lets a user OVERRIDE a bad/limited PDA-injected key (a key without `log` fetches no bust history), and a saved panel key takes priority over the injected one (see `getApiKey`). So it is a feature, but the UX makes new PDA users think they must enter a key twice.
  - Implemented (v2.15.0, `refreshApiKeyState`): when the PDA-injected key is present, right length, and not being rejected by Torn (`fatalKeyError`), the panel collapses the key box to the status line "API key is saved." (same text as a saved desktop key, per user preference) plus an opt-in "Not working? Use your own key instead" link (`#bustr-set-apikey-override`, latched via `apiKeyEntryForced`). The box stays open when the injected key is missing/empty, the wrong length, or being rejected.
  - **Still needs a real PDA before/after screenshot or debug export to confirm** (standing "don't guess at PDA" rule): verify the collapse actually triggers on a healthy injected key, that the override link reveals the field, and that a bad injected key still prompts.
- **Browser password-autofill (FIXED v2.15.0):** the panel key field was `type="password"`, which triggered the browser's built-in password manager to offer autofill in nearby Torn text boxes (e.g. chat search); it stopped when BUSTR was disabled. Now a masked `type="text"` (`-webkit-text-security`, not a password field) with `data-*ignore` hints for third-party managers. Verifiable on desktop; PDA unaffected either way.

## Model recalibration - the big finding (2026-08-07, from the first cross-user data analysis)
Ran `cloud/aggregate.js` against live Firestore: **13 users, 899 records (765 current-model m:2)**. First real cross-user look at the success model. `aggregate.js` was improved this session to (a) filter to `m:2` only (134 legacy rows have inflated pen / pred artifacts and were polluting the buckets) and (b) add a calibration-by-predicted-bucket table. Re-run it anytime with `cd cloud && node aggregate.js` (needs `npm install` once; it reads the gitignored `*adminsdk*.json`).

Findings (m:2 only):
- **Overall calibration is excellent on the mean:** 59.8% predicted vs 62.5% actual. But that hides an offsetting shape error at the two ends.
- **Penalty response is too steep.** Low penalty (0-79%) is over-predicted (~77-81% shown vs ~52-77% actual); high penalty (130-199%) is drastically UNDER-predicted - the model floors those to ~16% but they actually succeed ~68-90%. In the calibration table, the whole `pred ~16%` bucket (n=116) succeeds **67%**. Top buckets (pred 70-89, n~377) are ~10pts over-confident.
- Diagnosis: the linear `-2.0*penaltyPct` term (calcSuccessChanceRaw) over-penalises at the high end; penalty's real marginal effect saturates. This is exactly the "saturating curve" the v2.8.0/v2.10.0 notes predicted we'd need "once we have more than one player's data." We now do.

**Why no model change shipped yet (do NOT skip this):** a rigorous leave-one-out (the standing rule; the raised-floor idea already passed in-sample and FAILED LOO once) needs to recompute each record's prediction from its inputs - but historical records store only `h, pred, pen, success, jailed, ts, m`, omitting the `level` and `calibration` the formula needs, and stored `pred` mixes pre/post-shrink displays. So the data on hand cannot validate a fix.

**What was done instead (v2.15.1):** every new outcome now also logs `lvl` + `cal` (the exact inputs used), so future records are fully reconstructable. These sync for opted-in users, so cross-user enriched data will accumulate.

**Pipeline VERIFIED (2026-08-07):** `cloud/validate_enriched.js` recomputes each enriched record's prediction from its `h/pen/lvl/cal` and compares to the stored `pred` - 131/132 exact (99.2%), 1 off-by-one rounding, 0 real mismatches. So the captured data is internally consistent and trustworthy; the recalibration just needs volume. Latest aggregate: 16 users, 1311 m:2 records, but only ~132 enriched (lvl+cal) so far - the old ~1180 predate 2.15.1 and can't be backfilled. Data is well-spread (top user 28%). Signal unchanged and strong: ~40% of records floored to pred~16% but succeed ~55%; overall 46.5% predicted vs 59% actual. Re-run `cd cloud && node aggregate.js` (and `validate_enriched.js`) to track enriched-count growth; fit when it reaches a few hundred with good high-penalty coverage.

**Next-session plan for the actual fix (once enough `lvl`/`cal`-stamped records exist):**
1. Dump enriched m:2 records ({h, pen, success, lvl, cal}) - extend `aggregate.js` or a sibling script.
2. Recompute current-model prediction per record from h/pen/lvl/cal (replicate calcSuccessChanceRaw exactly: skill=lvl*cal; raw=266.6-(0.28*60/skill)*h-2.0*pen; shrink 45+0.65*(clamp(raw,1,100)-45)).
3. Fit + **leave-one-out** candidate penalty forms (saturating/log/capped penalty, and/or a lifted floor, and/or the linear->logistic shape switch) vs the current model on Brier. Ship ONLY what beats current out-of-sample. Constants stay principled, not per-player-overfit. See [[bustr-model-followups]].

- Original `@author` line (`Adobi & Ironhydedragon`) stays untouched. Contributions are credited as a second `@author` line for `The_Baron [1467784]`, matching the style the original script already uses for RussianRob.

- Every substantive script change gets a version bump (`@version` header + the `SCRIPT_VERSION` constant, keep them in sync) and a `CHANGELOG.md` entry, then regenerate BOTH `CHANGELOG_DISCORD.txt` and `CHANGELOG_FORUM.html` (`python changelog_to_forum.py`).
- Cloud sync rules that must never be broken: (a) the API key stays on the user's device - it may go only to Torn's API and once to the verification function, never stored server-side; (b) cloud sync is opt-in, default OFF, with explicit consent before the first enable; (c) the Firebase service-account JSON is the only secret and lives ONLY in the Netlify env var `FIREBASE_SERVICE_ACCOUNT` - never committed, never in the client, never pasted into chat; (d) the debug export must never contain the API key or the cloud auth session (`CLOUD_AUTH_KEY` is stored outside `state` deliberately).
- Full memory context (math validation history, UI placement history, authorship rules, etc.) is already in the persistent memory store for this project and should load automatically in a new session.
